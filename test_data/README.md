# AI Transparency on FHIR -- Connectathon 43 Test Data

Synthetic FHIR R4 test data for the AI Transparency on FHIR track, built to exercise
the track's testing scenarios and conform to the [AI Transparency on FHIR IG](https://build.fhir.org/ig/HL7/aitransparency-ig/en/).

All patient data is generated by [Synthea](https://github.com/synthetichealth/synthea)
(Massachusetts population); no real patient data is used. Clinical codes and values
were never altered by hand -- only resource selection, reference repair, ID rewriting,
AI security labels, AI Provenance, and the two hand-authored clinical notes were added.
See "Regenerating this data" below for exact seeds.

## What's here

```
infrastructure/infrastructure_bundle.json   3 AI Devices, 5 prompt DocumentReferences, 1 Practitioner
unlabeled/*_bundle.json                     2 patients, zero AI labels anywhere (+ a hand-written note each)
labeled/*_bundle.json                       20 patients, mixed AI-labeled / unlabeled resources
manifest.json                               machine-readable expected results for every verification query below
```

Every bundle is a FHIR transaction Bundle using `PUT` with client-assigned ids (not
`POST`), so loading is idempotent and every id is stable and known in advance.

## Load order

1. **`infrastructure/infrastructure_bundle.json`** first, always. Every patient bundle
   references its Devices (`Device/ai-device-1..3`), prompts
   (`DocumentReference/prompt-1..5`), and the verifier Practitioner
   (`Practitioner/practitioner-verifier`) by literal reference, and those references
   only resolve once the infrastructure bundle is loaded.
2. Then the `unlabeled/` and `labeled/` bundles, in any order -- they don't reference
   each other.

Each is a standalone transaction bundle; POST it to your server's base URL
(`POST [base]`) or use your server's batch-upload mechanism.

## The two data sets

### `unlabeled/` -- for participants building their own AI ingestion

Two patients with **no AI labels or Provenance anywhere**. The test: run the patient
(including the attached clinical note) through your own AI, produce a bundle where the
existing resources are untouched and any *new* resources you create are AI-labeled with
correct `AI-Provenance` pointing back at your own Device and at the note as the input
prompt/entity.

Each patient bundle includes one hand-written clinical note (`DocumentReference`, LOINC
`34109-9` "Note", `text/plain`) that is clinically consistent with the patient's coded
data but contains findings that are **not** represented anywhere else in the bundle --
these are the findings a participant's AI is expected to discover and turn into new,
correctly-labeled resources.

| Patient | Bundle | Note | Findings in the note NOT already coded in the bundle |
|---|---|---|---|
| Lacey Berge (56F; chronic kidney disease, type 2 diabetes, asthma) | `unlabeled/lacey_berge_bundle.json` | `unlabeled/lacey_berge_note.md` | Elevated BP (148/92); new drug allergy to lisinopril (rash); asthma symptom detail (exertional dyspnea, twice-weekly rescue inhaler use) |
| Branden Mayer (101M; hypertension, ischemic heart disease s/p CABG, prediabetes) | `unlabeled/branden_mayer_bundle.json` | `unlabeled/branden_mayer_note.md` | Elevated BP (162/94) and HR; new drug allergy to a sulfa antibiotic (hives, lip swelling); orthostatic-lightheadedness symptom detail |

### `labeled/` -- for Scenarios 1-4

Twenty patients, each with a realistic mix of AI-labeled and untouched resources.
AI labeling only ever touches these resource types (per the IG, resource-level labeling
only): `Observation`, `Condition`, `DiagnosticReport`, `AllergyIntolerance`,
`MedicationRequest`. Every AI-labeled resource has `meta.security` containing the
`AIAST` ("Artificial Intelligence asserted") code, and exactly one `Provenance`
conforming to the `AI-Provenance` profile targeting it, with:

- `agent` author = one of the 3 AI Devices in `infrastructure_bundle.json` (never
  contained -- always `Device/ai-device-1|2|3`)
- `entity.what` = one of the 5 prompt `DocumentReference`s in
  `infrastructure_bundle.json` (never contained -- always
  `DocumentReference/prompt-1..5`), reused across multiple Provenances and patients
- about half of Provenances additionally have a `verifier` agent referencing
  `Practitioner/practitioner-verifier` (human-in-the-loop), so both the reviewed and
  unreviewed case are represented (Scenario 1)

Every patient has at least 2 AI-labeled and at least 5 untouched resources (Scenario 2),
every device's resource set is disjoint from the others' and spans at least 5 different
patients (Scenario 3), and every prompt is reused by at least 3 Provenances spanning at
least 2 patients, with no single device or prompt covering the whole data set
(Scenario 4).

The 3 AI Devices represent distinct kinds of AI (see `AIdeviceTypeCS`):

| Device | Identity | AIKind |
|---|---|---|
| `ai-device-1` | ScribeAssist LLM | `Large-Language-Models` |
| `ai-device-2` | TextXtract NLP Pipeline | `AI-for-Medical-Text-Data` |
| `ai-device-3` | EarlyWarn Risk Model | `Machine-Learning-Models` |

The 5 prompts (`prompt-1` mainly used by `ai-device-1`, `prompt-2` shared between
`ai-device-1` and `ai-device-3`, `prompt-3`/`prompt-4` used by `ai-device-2`, `prompt-5`
mainly used by `ai-device-3`) are summarization, structured-data-extraction, and
risk-scoring prompts consistent with each device's kind -- see
`infrastructure_bundle.json` for the full prompt text.

## Verification queries

All expected counts are recomputed and cross-checked against `manifest.json` by
`script/validate_data.py`; the numbers below are the current values for the seeds
recorded under "Regenerating this data".

### Scenario 3 -- recall by model (`Provenance?agent=Device/<id>`)

| Query | Expected results | Distinct patients touched |
|---|---|---|
| `GET /Provenance?agent=Device/ai-device-1` | 40 | 7 |
| `GET /Provenance?agent=Device/ai-device-2` | 34 | 7 |
| `GET /Provenance?agent=Device/ai-device-3` | 32 | 6 |

Total AI-labeled resources across the labeled set: **106**. Each device's result set is
a proper subset (40, 34, and 32 are all < 106) and the three sets are disjoint --
querying `ai-device-1` never returns a resource produced by `ai-device-2` or
`ai-device-3`.

### Scenario 4 -- recall by input (`Provenance?entity=DocumentReference/<id>`)

| Query | Expected results | Distinct patients touched |
|---|---|---|
| `GET /Provenance?entity=DocumentReference/prompt-1` | 29 | 7 |
| `GET /Provenance?entity=DocumentReference/prompt-2` | 19 | 13 |
| `GET /Provenance?entity=DocumentReference/prompt-3` | 24 | 7 |
| `GET /Provenance?entity=DocumentReference/prompt-4` | 10 | 7 |
| `GET /Provenance?entity=DocumentReference/prompt-5` | 24 | 6 |

`prompt-2` is shared across `ai-device-1` and `ai-device-3`'s patients, so querying by
`prompt-2` returns a different -- and non-trivial -- subset than querying by any single
device (13 patients spanning two device groups vs. 6-7 patients for a single device).

### Scenario 1 / 2 -- attribution and filtering

Every resolved `Provenance.target` for a labeled resource can be checked against
`manifest.json` to confirm exactly one `Provenance` per AI-labeled resource, and
whether it carries a `verifier` agent (human-reviewed) or author-only (unreviewed).
For per-patient AI-labeled vs. untouched counts (needed to test risk-based filtering),
see `manifest.json`'s `patients` section, e.g.:

```
GET /Observation?subject=Patient/<id>&_security=AIAST   -> manifest.patients["Patient/<id>"].ai_labeled AI-labeled Observations (plus other labeled types)
```

## Regenerating this data

```
# 1. Generate raw Synthea output (from /Users/sschifma/DEV/other_tools/synthea):
./run.sh -p 30 Massachusetts

# 2. Trim a Synthea bundle (repeat per selected patient; seed 42 was used for all
#    20 labeled patients and for branden_mayer; seed 1 --max-encounters 8 for lacey_berge):
python3 script/trim_bundle.py --input <synthea_bundle>.json --output <trimmed>.json --seed 42

# 3. Label a trimmed bundle for the labeled set (see script/label_bundle.py --help;
#    the exact per-patient device/prompt/count/seed used for this data set is a fixed
#    plan -- 7 patients on ai-device-1 with prompt-1/prompt-2, 7 on ai-device-2 with
#    prompt-3/prompt-4, 6 on ai-device-3 with prompt-5/prompt-2):
python3 script/label_bundle.py --input <trimmed>.json --output <labeled>.json \
    --seed <n> --device ai-device-1 --prompt prompt-1 --prompt prompt-1 --prompt prompt-2 \
    --count <n> --verifier-fraction 0.5

# 4. Validate everything:
python3 script/validate_data.py
```

`test_data/manifest.json` is the source of truth for expected counts; regenerating with
different seeds will change the numbers above and requires regenerating the manifest
too (recompute device/prompt -> target maps from the bundles, as `validate_data.py`
does).
